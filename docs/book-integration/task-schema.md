# Задачи Judge: контракт для книг

> **Версия схемы: 1** · [JSON Schema](./task-schema.json)

Книга публикует `tasks.json` как ассет своего GitHub Release'a.
BSLexicon читает его на build-этапе, валидирует JSON Schema и
кладёт в bundle раздела `/judge/`.

## Почему релиз-ассет, а не raw с ветки

Мы уже наступили на переименование репозиториев: `raw.githubusercontent.com`
не редиректит, и «внезапно нулевая» задача у читателя — плохая история.
Release-ассет — версионный указатель, ссылка стабильна независимо от
того, как автор двигает файлы внутри репо.

BSLexicon в `catalog/books.yaml` хранит `{book_id, repo, min_version}` —
и берёт `tasks.json` из `releases/tag/<pinned>`, а не с ветки.

## Пайплайн со стороны книги

1. Автор пишет задачи в `tasks/<slug>.yaml` (по одному файлу, чтобы диффы
   были локальными).
2. `book.sh` собирает их в один `tasks.json` при `release` — сортирует
   по главе, валидирует по нашей [`task-schema.json`](./task-schema.json).
3. GitHub Action публикует ассет `tasks.json` рядом с EPUB/PDF.

BSLexicon у себя `npm run fetch:book-tasks` тянет каждый tasks.json из
книг registry, снова валидирует, кладёт в `public/reference/judge-<book_id>.json`.
При невалидном JSON CI тренажёра падает громко — читатель не увидит
битую задачу.

## Ключевые правила

- **id стабилен навсегда** — прогресс читателя хранится по `<book_id>:<task_id>`.
- **Один листинг в одном месте.** Sandbox-примеры остаются в главах
  (`bsl,песочница`), задачи с проверкой — только в `tasks/`. Дублировать
  «код-пример из главы как задачу» нельзя: рассинхронизуется.
- **Тесты — за читателя, не против автора.** Скрытые тесты для крайних
  случаев уместны, но большинство должно быть открытыми: читатель должен
  понимать, что именно он не проходит.
- **Условие — plain markdown.** Без HTML, без макросов книги. У BSLexicon
  свой рендерер — экзотические расширения не поддерживаем.

      "statement": "Реализуй функцию `СуммаСписка(Перечень)` — на вход строка вида\n`\"1,2,3\"`, возвращает сумму чисел. Пустая строка → 0.\n\nПодсказка: `СтрРазделить(Перечень, \",\")` возвращает массив строк,\nкаждую нужно превратить в число через `Число()`.",

      "difficulty": "easy",
      "tags": ["массив", "цикл", "строки"],
      "tests": [
        { "kind": "call", "name": "три числа", "invoke": "СуммаСписка(\"1,2,3\")", "expect": "6" },
        { "kind": "call", "name": "одно число", "invoke": "СуммаСписка(\"42\")", "expect": "42" },
        { "kind": "call", "name": "пустая строка", "invoke": "СуммаСписка(\"\")", "expect": "0" },
        { "kind": "call", "name": "с отрицательными", "invoke": "СуммаСписка(\"-5,5,10\")", "expect": "10", "hidden": true }

## Виды тестов

Ровно два — `stdout` и `call`. Оба выражают одну идею: «запусти
starter + решение читателя, потом сравни».

### `kind: "stdout"`

Ожидаем определённый вывод `Сообщить()`. Многострочный `expect`
сравнивается построчно, лишние пробелы в конце строк игнорируются.

```json
{ "kind": "stdout", "expect": "Привет, мир!" }
```

Годится для первых глав, когда функций у читателя ещё нет.

### `kind: "call"`

Ожидаем, что выражение `invoke` вернёт значение `expect`. Выражение
`invoke` дописывается ПОСЛЕ кода читателя, поэтому имеет доступ ко всем
объявленным функциям.

```json
{ "kind": "call", "invoke": "Скидка(1500)", "expect": "0.1" }
```

`expect` — литерал BSL: число (`6`, `0.1`), строка в кавычках (`"да"`),
`Истина`/`Ложь`/`Неопределено`. Сравнение deep-equality (на стороне
интерпретатора).

#### ⚠ Ограничение `call`: коллекции нельзя передать аргументом

В BSL **нет литерала массива** (`[1, 2, 3]` не существует), а `Новый
Массив(N)` создаёт массив _размерности_ N, а не с элементами N. Поэтому
`Новый Массив(1, 2, 3)` — это трёхмерный пустой массив, а не `[1, 2, 3]`.

Значит `invoke` (одно выражение) не может передать коллекцию функции.
Два обхода:

- **Данные приходят строкой**, функция сама её разбирает через
  `СтрРазделить` (см. пример выше).
- **Пишем тест `stdout`**, где стартовый код собирает коллекцию
  и функция обрабатывает её.

Это ограничение самого языка, не тренажёра.

### Скрытые тесты

`"hidden": true` — читатель видит только ✓/✗ и никаких деталей.
Полезно для крайних случаев (пустой массив, отрицательные значения),
чтобы решение проходило не только «happy path». **Не** используем
скрытые тесты как основной путь: если из 5 тестов открыт только один,
задача превращается в угадайку.

## Стабильность и версионирование

- `book.version` — SemVer книги. Задачи из `0.9.0` и `0.9.5` совместимы;
  из `0.x` и `1.0` — нет.
- Изменение `id` задачи = удаление старой + добавление новой. Прогресс
  сбросится. Не переименовываем.
- Изменение `starter` мажорно (сбивает работу читателя) — только между
  версиями книги. Внутри одной версии starter стабилен.

Мы можем менять UI задачи, добавлять поля в схему — но `id`/`title`/
`tests` — это контракт с читателем, а не с автором.
