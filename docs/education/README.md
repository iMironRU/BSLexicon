# Учебная платформа BSLexicon

> **Статус:** дизайн-документ, реализация по этапам (см. `roadmap` внизу).
> **Дата:** 2026-09-08
> **Назначение:** система обучения BSL «педагог + ученик + git» поверх notebook-режима.

---

## 1. Что это

Расширение `/notebook/` до учебной платформы. Ноутбук — уже не только личный черновик, а способ **отдать учебный материал** ученику и **получить решение обратно**.

Три сущности:
- **Задача** (`.task.yaml`) — переиспользуемый файл в git-репо педагога. Формат совместим с [книжной интеграцией](../book-integration/task-schema.md) v1.
- **Ноутбук-урок** (`.nb.json`) — файл в git-репо педагога. Содержит markdown-объяснения и task-cell'ы, которые ссылаются на задачи по `ref`.
- **Решение ученика** (`.nb.json`) — файл в личном git-репо ученика. Копия ноутбука педагога + свои ответы в task-cell'ах + snapshot версии.

Педагог отдаёт ссылку → ученик открывает → решает → сдаёт ссылкой на свой файл.

Никакого сервера у BSLexicon по-прежнему нет. Всё живёт в git-репозиториях сторон. BSLexicon — тонкий фронтенд поверх статичных файлов.

---

## 2. Роли

Два режима работы в UI notebook'а — [issue #27](https://github.com/iMironRU/BSLexicon/issues/27):

### Педагог (author)

Видит и делает:
- Редактирует условия/тесты/подсказки в task-cell'ах через форму
- Добавляет/удаляет/переставляет ячейки любого типа
- Кнопка **📁 Мои ноутбуки** — список файлов из своего git-репо
- Кнопка **📚 Задачи** — библиотека `.task.yaml` из своего git-репо
- Кнопка **💾 Сохранить как** / **↑ Push** / **↓ Pull**
- Кнопка **🔗 Поделиться уроком** — генерирует `?nb-src=<raw-url>` для ученика

### Ученик (student)

Видит и делает:
- Редактирует своё решение в code- и task-ячейках
- Запускает ▶ на code, «▶ Проверить» на task
- Разворачивает подсказки
- Кнопка **📤 Отправить педагогу** — сохраняет копию с решениями в свой git-репо, копирует URL для отправки педагогу

Не видит:
- Формы редактирования task-spec
- Контролов ↑↓✕ и кнопок «+ …»

Дефолт при открытии:
- `?nb=…` (полный ноутбук в URL) — **student**
- `?nb-src=…` (ссылка на git) — **student**
- Без параметров, из localStorage draft — **author**

Toggle в хедере всегда доступен — student может «раскрыть» и посмотреть spec (это фронтовая условность, не защита).

## 3. Хранилище

### Педагог

```
tasks-repo/                       ← репо педагога
  tasks/
    strings-length.task.yaml
    loops-for.task.yaml
    collections-array-basics.task.yaml
  notebooks/
    lesson-01-strings.nb.json     ← task-cell ссылается на tasks/strings-length.task.yaml
    lesson-02-loops.nb.json
  README.md                        ← опционально: список уроков для людей
```

Одна задача может использоваться в нескольких уроках. Обновил задачу — все уроки автоматически подхватят (при следующем открытии учеником).

### Ученик

```
solutions-repo/                   ← личный репо ученика
  solutions/
    ivanov-lesson-01-strings.nb.json
    ivanov-lesson-02-loops.nb.json
```

Сохранение решения = коммит в этот репо. Ученик отдаёт педагогу raw-ссылку на конкретный файл.

Оба репо подключаются через существующий git-connect BSLexicon (`src/app/git-config.ts` — PAT в localStorage, никаких прав на аккаунт).

## 4. Форматы

### 4.1 `.task.yaml` — задача

Переиспользуем схему [`task-schema.json`](../book-integration/task-schema.json) v1 (уже работает для книг). Одно отличие: отдельно стоящая задача не привязана к книге, поэтому `chapter`, `section`, `book_url` опциональные.

Пример `tasks/strings-length.task.yaml`:

```yaml
id: strings-length
title: Длина строки
difficulty: easy
tags: [строки, встроенные-функции]

statement: |
  ## Длина строки

  Дана строка `С = "мир"`. Выведи её длину функцией `Сообщить(СтрДлина(...))`.

starter: |
  С = "мир";
  // выведи длину

tests:
  - kind: stdout
    expect: "3"

hints:
  - Функция называется `СтрДлина`.
  - Не забудь `Сообщить(...)` — иначе результат не увидишь.
```

### 4.2 `.nb.json` — ноутбук

Сериализованный `Notebook` объект. Формат — расширенный вариант того что уже пишется в localStorage draft:

```json
{
  "v": 1,
  "cells": [
    { "t": "md", "s": "# Урок про строки\n\nСегодня разберём..." },
    { "t": "code", "s": "С = \"привет\";\nСообщить(СтрДлина(С));" },
    {
      "t": "task",
      "s": "",
      "ref": "tasks/strings-length.task.yaml"
    }
  ]
}
```

Ключевое отличие от локального `?nb=`: task-cell содержит `ref` вместо inline `task` spec. При рендере тренажёр резолвит `ref` относительно расположения `.nb.json` в репо.

Backward-compat: inline `task` продолжает работать (для ноутбуков без git-репо, шаринг через `?nb=`).

### 4.3 Snapshot решения ученика

Файл решения ученика — тот же формат `.nb.json`, но task-cell содержит **и `ref`, и inline `task` snapshot**, плюс `s` — решение ученика:

```json
{
  "v": 1,
  "source": {
    "repo": "pedagog/tasks-repo",
    "sha": "abc1234def",
    "nb_path": "notebooks/lesson-01-strings.nb.json"
  },
  "cells": [
    { "t": "md", "s": "# Урок про строки..." },
    {
      "t": "task",
      "s": "С = \"мир\";\nСообщить(СтрДлина(С));",
      "ref": "tasks/strings-length.task.yaml",
      "task_snapshot": {
        "statement": "…",
        "starter": "…",
        "tests": [{ "kind": "stdout", "expect": "3" }]
      }
    }
  ]
}
```

**Зачем snapshot:** педагог может обновить `strings-length.task.yaml` пока ученик решает. Решение сохраняется с копией spec **и с git-SHA репо педагога на момент открытия**. Педагог, глядя на решение, видит:
- Какой SHA его репо был при открытии ученика
- Какая версия задачи была на тот момент (в `task_snapshot`)
- Результат прогонки — против этого snapshot, не против текущего HEAD

Это защита от «моё решение внезапно перестало проходить, потому что учитель изменил тесты».

## 5. URL-контракт

Два новых параметра к существующим (`?nb=`, `?code=`, `?gzcode=`):

### `?nb-src=<raw-github-url>`

Ученик открывает ноутбук по прямой ссылке. Тренажёр:
1. Загружает `.nb.json` из URL.
2. Резолвит `ref` в task-cell'ах относительно того же raw-пути.
3. Загружает нужные `.task.yaml` файлы.
4. Сохраняет git-SHA репо на момент открытия (в state — для будущего snapshot'а решения).

Пример:
```
https://imironru.github.io/BSLexicon/notebook/
  ?nb-src=https://raw.githubusercontent.com/pedagog/tasks-repo/main/notebooks/lesson-01-strings.nb.json
```

### `?mode=student` / `?mode=author`

Форсирует режим. Умный дефолт (см. §2) применяется если параметр не задан.

## 6. Flow

### Педагог готовит урок

1. Подключает свой репо в BSLexicon (git-config, единый для трен./ноутбука).
2. Открывает `/notebook/` → режим author по дефолту.
3. Собирает ноутбук: markdown, code, task-cell'ы. Task-cell'ы либо inline (не переиспользуются), либо ссылаются на `.task.yaml` в своём `tasks/`.
4. **↑ Push** → файл `notebooks/lesson-01.nb.json` попадает в репо.
5. **🔗 Поделиться уроком** → в буфер:
   ```
   https://imironru.github.io/BSLexicon/notebook/
     ?nb-src=https://raw.githubusercontent.com/…/lesson-01.nb.json
   ```

### Ученик решает

1. Открывает ссылку от педагога → режим student, ноутбук + задачи подгружены.
2. Тренажёр фиксирует git-SHA (например, HEAD `main` репо педагога на момент open).
3. Ученик решает task-cell'ы. Проверка — против snapshot'а spec из момента open (не против текущего HEAD).
4. **📤 Отправить педагогу**:
   - Просит подключить свой репо (если ещё не подключён).
   - Пушит `solutions/ivanov-lesson-01.nb.json` со всеми решениями + snapshot'ом.
   - Копирует raw-URL этого файла в буфер.
5. Ученик отдаёт эту ссылку педагогу (мессенджер, email, что угодно).

### Педагог смотрит решение

1. Открывает ссылку ученика в `/notebook/?nb-src=…` — режим student (для просмотра), toggle → author (для комментария/оценки).
2. Видит все ячейки с решениями ученика. task_snapshot говорит какая была задача — даже если педагог обновил `main` со вчера.
3. Прогоняет проверку — тесты идут против snapshot'а (=тех что видел ученик).
4. Опционально — оставляет пометки в файле решения ученика (`fork` + PR, или прямой push если у педагога права).

## 7. Что осознанно НЕ делаем

- **Свой сервер** для класса, реестра учеников, автоматической рассылки заданий. Всё через git-репозитории сторон, ссылки в мессенджерах.
- **Аутентификацию** между педагогом и учеником. Идентификация ученика = raw-ссылка на его файл, которую он даёт сам. Пришёл кто-то чужой с ссылкой — педагог видит по имени репо / файла.
- **Оценки внутри BSLexicon.** Педагог может оставить комментарий в решении, но UI-оценок нет.
- **Автоматическое обновление ноутбука ученика** при изменении педагогом задачи. Snapshot по SHA — единственный источник истины для конкретной попытки.
- **Приглашения / список учеников.** Педагог сам ведёт список репозиториев своих учеников (может быть отдельный `students.yaml` в репо педагога, но UI-поддержка — не в первом заходе).

## 9. Открытые вопросы

- Формат идентификатора для педагога: `pedagog/tasks-repo` — что если репо переименовали? Записываем SHA + repo — при renamed репо ученик может открыть через новое имя, но snapshot жив.
- Приватные репо: BSLexicon PAT ученика имеет права только на его репо. Значит педагогические `.task.yaml` должны быть в **публичном** репо, чтобы ученики могли их читать. Или педагог передаёт PAT ученикам — плохая практика.
- Резолв cross-file ссылок: `.nb.json` в `notebooks/`, ссылается на `tasks/…` — как понять корень репо? Считаем что репо это monorepo, `.nb.json` знает свой path через URL. `ref` в task-cell — относительно корня репо (`tasks/x.yaml`) или относительно ноутбука (`../tasks/x.yaml`)? Рекомендую **относительно корня** — стабильнее при переносе.
- Кэширование раздачи задач: HTTP GET по raw.githubusercontent.com — не медленно ли? Обычные CDN'ы это отдают быстро, но при 30 задачах в ноутбуке — 30 запросов. Возможно введём **манифест** `notebooks/lesson-01.manifest.json` со списком задач и их inline'ами — оптимизация на потом.

## 10. Связь с существующим

- **Книжная интеграция** ([`../book-integration/`](../book-integration/)) — переиспользуем `task-schema.json` v1, единый формат задач. Педагог может публиковать свой репо как книгу-partner (`catalog/books.yaml`), тогда задачи попадают ещё и в `/help/judge/`.
- **Тренажёр git-connect** — используем тот же `src/app/git-config.ts`. Один PAT — все страницы (тренажёр, notebook).
- **Notebook MVP** — persistent kernel (#23), task-cell (#24), автосохранение (#25) остаются в силе. Учебная платформа — надстройка над MVP.
