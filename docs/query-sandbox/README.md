# Песочница языка запросов 1С

> **Статус:** дизайн-документ, реализация по этапам.
> **Дата:** 2026-09-08
> **Назначение:** учебный тренажёр языка запросов 1С — с редактором, схемой, тестовыми данными и автопроверкой.

---

## 1. Что это

Дополнение к BSLexicon: ученик пишет запрос на языке запросов 1С, тренажёр выполняет его над **учебной моделью данных** и показывает результат. Педагог задаёт задачи, проверка автоматическая.

Педагогически это **третий столп**:
- **Тренажёр BSL** — синтаксис языка (реализовано)
- **Notebook + учебная платформа** — курс с ячейками, задачами, сдачей (реализовано)
- **Query-sandbox** — язык запросов (эта штука)

Как и всё в BSLexicon: **без сервера**. Схема + данные + запросы живут в git-репозиториях сторон и в браузере.

## 3. Три стратегии реализации движка

Сравнение (обоснование в §4-§6):

| Стратегия | Сложность | Полнота 1С-семантики | Скорость | Комментарий |
|---|---|---|---|---|
| **A. Свой interpreter** над in-memory таблицами | Высокая | Полная | Средняя | Учит РЕАЛЬНОЙ семантике 1С; поддерживает всё что напишет автор парсера |
| **B. Только парсер + подсветка + autocomplete**, без выполнения | Низкая | — | — | Учит писать; не проверить; ~50% педагогической ценности |
| **C. Транспиляция ЯЗ → SQL + sql.js** (SQLite WASM) | Средняя-высокая | ~85% (`ИТОГИ ПО`, виртуальные таблицы регистров — сложно) | Отличная | Не пишем execute engine; часть семантики теряется |

**Гибрид B+C** реалистичнее всего: **начинаем с B** (парсер + подсветка + autocomplete, «синтаксический тренажёр»), **дополняем C** (простые SELECT/WHERE/JOIN через sql.js). `ИТОГИ ПО` и виртуальные таблицы регистров — отдельным шагом.

## 4. Модель данных

Ключевой вопрос: **где брать схему и данные**.

### 4.1 Три источника

**A. Встроенная демо-схема.** Одна на весь тренажёр, живёт в коде. Учебная упрощённая ERP (5-10 объектов, 50-200 записей). Ученик открывает `/query/` — сразу есть на чём писать.

**B. Педагог задаёт схему в git-репо** (тот же что у нас уже есть — единый git-connect):
```
schemas/
  chapter-01.schema.yaml   ← схема для одной главы урока
  chapter-01.data.yaml     ← тестовые данные под неё
  chapter-02.schema.yaml
  chapter-02.data.yaml
```
YAML — простой, педагог задаёт руками.

**C. XML 1С — универсальная выгрузка** (см. отдельно ниже).

**Стратегия:** делаем **A + B в MVP**, C — как «загрузчик» отдельным шагом.

### 4.2 Формат A/B — YAML

Схема (`chapter-01.schema.yaml`):
```yaml
version: 1
tables:
  - kind: Справочник
    name: Номенклатура
    fields:
      - { name: Ссылка, type: UUID, key: true }
      - { name: Код, type: Строка(9) }
      - { name: Наименование, type: Строка(150) }
      - { name: Родитель, type: Ссылка, refs: Справочник.Номенклатура }
      - { name: ПометкаУдаления, type: Булево }

  - kind: Документ
    name: РасходнаяНакладная
    fields:
      - { name: Ссылка, type: UUID, key: true }
      - { name: Номер, type: Строка(11) }
      - { name: Дата, type: Дата }
      - { name: Контрагент, type: Ссылка, refs: Справочник.Контрагенты }
    tabular:
      - name: Товары
        fields:
          - { name: Номенклатура, type: Ссылка, refs: Справочник.Номенклатура }
          - { name: Количество, type: Число(15,3) }
          - { name: Сумма, type: Число(15,2) }
```

Данные (`chapter-01.data.yaml`):
```yaml
version: 1
records:
  Справочник.Номенклатура:
    - { Ссылка: "n1", Код: "000000001", Наименование: "Молоток", Родитель: null, ПометкаУдаления: false }
    - { Ссылка: "n2", Код: "000000002", Наименование: "Отвёртка", Родитель: null, ПометкаУдаления: false }

  Документ.РасходнаяНакладная:
    - Ссылка: "d1"
      Номер: "0000000001"
      Дата: "2024-01-15T10:00:00"
      Контрагент: "k1"
      Товары:
        - { Номенклатура: "n1", Количество: 5, Сумма: 500 }
        - { Номенклатура: "n2", Количество: 3, Сумма: 450 }
```

Плюсы:
- Педагог пишет руками, читаемо в git.
- Маленький (KB), диффабельно.
- Легко валидировать JSON-схемой.

### 4.3 XML 1С — универсальная выгрузка

**1С-разработчики уже знают как получить это:**
- Конфигуратор → Администрирование → Выгрузить данные (в набор XML файлов)
- Обработка «Выгрузка/Загрузка данных XML» из БСП
- Через `Data Format Description` (XDTO)

Каждый объект = отдельный XML-файл или блок. Ссылки — GUID. Табличные части — вложенные списки.

**Плюсы:**
- Педагог берёт реальную (маленькую) конфу, выгружает — файлы уже готовы.
- Совместимость с миром 1С — учебник может использовать любую демо-базу.
- Данные + метаданные вместе.

**Минусы:**
- Полная выгрузка нормальной конфы = 100+ МБ, браузер не тянет.
- Формат громоздкий — парсер XML в браузере медленный на больших объёмах.
- Не все конструкции метаданных ясно маппятся в реляционную модель (составные типы, роли, формы).

**Реальный подход:**

1. **Учебный формат** (наш YAML) — для маленьких схем «под конкретную главу».
2. **XML 1С — импортёр «обрезалка»**: педагог грузит выгрузку, тренажёр:
   - парсит структуру объектов метаданных (только `Configuration.xml` и близкие)
   - показывает список объектов, педагог **выбирает** нужные (10-30)
   - опционально грузит данные, но **только выбранных объектов**
   - экспортирует в наш YAML-формат
   - педагог кладёт YAML в свой git

По сути XML 1С — **инструмент импорта**, не runtime-формат.

Отдельным issue: [#39 XML-импортёр](https://github.com/iMironRU/BSLexicon/issues/39) (будет).

### 4.4 Учебная демо-схема (что будет в коде)

Мини-ERP:
- Справочник.Номенклатура (5-15 позиций, иерархия)
- Справочник.Контрагенты (5-10 позиций)
- Справочник.Склады (2-3 позиции)
- Документ.РасходнаяНакладная (5-10 док-в с табл. частью Товары)
- **РегистрНакопления.ОстаткиТоваров** — движения от РасходнаяНакладная. Виртуальные `Остатки/Обороты/ОстаткиИОбороты`.
- **РегистрСведений.ЦеныНоменклатуры** — периодический, ключ = Номенклатура, ресурс = Цена. `СрезПоследних(&Дата)` вернёт актуальные цены. Ученик может присоединять цены к товарам в накладной по дате документа.

С этой схемой ученик может писать: SELECT/WHERE/JOIN/GROUP BY/агрегаты/иерархия, виртуальные таблицы регистров накопления и сведений — базу первой-второй главы учебника.

## 5. URL-контракт и интеграция

По аналогии с notebook:

### 5.1 Прямая ссылка на песочницу

```
/query/?schema-src=<raw-url schema.yaml>&data-src=<raw-url data.yaml>&q=<url-safe base64 gzip запрос>
```

- `schema-src` / `data-src` — URL на файлы схемы и данных в репо педагога
- `q` — начальный запрос (аналог `?nb=`)
- Без параметров — открывается со встроенной демо-схемой

### 5.2 Ячейка в notebook

Четвёртый тип ячейки в notebook: `query`. Спека:
```json
{
  "t": "query",
  "s": "ВЫБРАТЬ * ИЗ Справочник.Номенклатура",
  "schema": { ... },   // inline
  "data": { ... },     // inline
  "tests": [ ... ]     // ожидаемый результат для Judge
}
```
Или ссылки через `ref` — как для task-cell (#28).

Ячейка ведёт себя как task-cell: условие + starter + автопроверка.

### 5.3 Задача-запрос для Judge

Формат `.query-task.yaml`:
```yaml
title: Все товары дороже 100 рублей
statement: |
  Напиши запрос, который вернёт наименование и цену всех
  товаров дороже 100 рублей.
schema-ref: chapter-01.schema.yaml
data-ref: chapter-01.data.yaml
starter: |
  ВЫБРАТЬ
      // TODO: список полей
  ИЗ
      Справочник.Номенклатура
  ГДЕ
      // TODO: условие
expected:
  columns: [Наименование, Цена]
  rows_unordered:
    - [Молоток, 500]
    - [Отвёртка, 150]
```

**Как сравнивать результат:**

- **columns** — обязательно точный порядок
- **rows_ordered** — если задача про `УПОРЯДОЧИТЬ ПО`
- **rows_unordered** — иначе, порядок не важен
- Типы: строгие (число != строка), но `Число(2)` == `Число(5)` если значения равны
- NULL vs 0 vs "" — различаем

Задачи-запросы попадают в тот же Judge-flow что и задачи по BSL, просто другой runner.

## 7. Открытые вопросы

Разбиты на **блокирующие** (решить до старта соответствующего этапа) и **тактические** (можно откладывать).

### 7.1 Блокирующие — требуют явного решения

**Q1. Стратегия движка: A — свой interpreter.** ✓ Решено.
- **Почему не C (sql.js):**
  - OSS транспилятора ЯЗ 1С в JS нет (см. `registers-research.md`) — C не «взять готовое», а «написать своё, потом ещё sql.js прикрутить».
  - Виртуальные регистры материализуем сами в обеих стратегиях — главный кусок сложности одинаковый.
  - Учебные объёмы (сотни-тысячи строк) — оптимизации SQLite не нужны.
  - Точная семантика 1С важна педагогически: типы (Число(15,3), Дата, Ссылка), NULL, ошибки в русскоязычных терминах.
  - +1.2 МБ gzip WASM ради того что делаем в ~2-3К строк TS — не окупается.
  - Общая инфра с BSL runtime: типы `BslValue`, значения, ошибки, часть функций (ГОД, МЕСЯЦ) — переиспользуются.
- **Что это значит:** interpreter над in-memory таблицами, каждый оператор ЯЗ (SELECT/JOIN/GROUP BY/агрегаты/скалярные функции) — своя реализация над `BslValue[]`.
- **Оценка:** 2-3 недели MVP-interpreter (базовые операторы), +виртуальные регистры/ИТОГИ/пакеты по roadmap.

**Q2. Модель регистров: «сырые движения + ленивый bucket-снимок по дню».** ✓ Решено.
- См. подробный research в [`registers-research.md`](./registers-research.md).
- Хранилище — массив движений, отсортированный по (Период, Регистратор).
- `Обороты(&Н, &К, dims)` — линейная свёртка по срезу (~200 строк TS, достаточно для учебных объёмов до 10k движений).
- `Остатки(&Дата, dims)` — префиксная сумма по группам измерений до `&Дата`, мемоизированная по границам суток (bucket = день, не месяц как в реальной 1С — учебные датасеты обычно короче).
- `ОстаткиИОбороты` — композиция первых двух.
- **Почему не как в 1С (месячные снимки):** учебные датасеты малы, месячный снимок ничего не экономит; дневной bucket достаточно.
- **Почему не DuckDB-Wasm:** 3-5 МБ WASM ради задач, решаемых в ~200 строках TS. Держим DuckDB как fallback для «больших» датасетов если появятся.
- **Педагогическая связь:** «Остатки на дату = префиксная сумма движений» ложится 1:1 на SQL оконную функцию `SUM(x) OVER (PARTITION BY ... ORDER BY period)` — удобный мостик к теме window functions.

**Q2a. Какие виды регистров реализуем.** ✓ Решено.
- Регистр в 1С — это семейство: **Накопления**, **Сведений**, **Бухгалтерии**, **Расчёта**. Разные механизмы, разная сложность.
- **Делаем:**
  - **Регистр накопления** — `Остатки(&Дата)`, `Обороты(&Н, &К)`, `ОстаткиИОбороты`. Модель: prefix sum движений (см. Q2). Issue #44.
  - **Регистр сведений** — `СрезПоследних(&Дата)`, `СрезПервых(&Дата)`, для периодических. Для непериодического — обычная таблица. Модель: «последняя запись до даты по каждой комбинации измерений». Проще накопления (без накопления, только выборка), ~100-150 строк TS. Issue #47.
- **Не делаем:** Регистр бухгалтерии (двойная запись, счета, корр.счета — крупная отдельная предметная область), Регистр расчёта (нишевая).
- **Почему такой выбор:** накопления + сведения покрывают ~95% типовых запросов «на регистры» в учебных курсах 1С. Бухгалтерия и расчёт — предметно-специфичные, требуют отдельного учебного контекста.

**Q3. Стандартная демо-схема + возможность произвольной.** ✓ Решено (комбинация).
- Стандартная мини-ERP (см. §4.4) живёт в коде — открытие `/query/` без параметров сразу даёт схему и данные, ученик может писать запросы за 0 секунд.
- Педагог может подложить свою через `?schema-src=<url>&data-src=<url>` или через ссылку `ref` в query-cell notebook'а.
- **Сетевой эффект + гибкость** одновременно: стандартная — общий словарь курсов «первого знакомства», авторские схемы — для узких тем (учёт по проекту, отдельная предметная область).
- **Следствие для #36:** формат YAML — один для обеих (стандартная зашита в коде через тот же loader что читает YAML педагога).
